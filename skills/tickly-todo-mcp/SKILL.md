# Tickly Todo MCP

通过 Tickly MCP 管理 Todo 时，优先保证任务身份、范围和变更结果准确；不要为了完成一句自然语言请求而猜测缺失信息或越过 MCP 能力边界。

## 适用范围

- 用户要求查询、创建、更新、完成或整理 Tickly Todo。
- 用户提到主题、父任务、状态、截止时间、任务流水号或批量修改。
- 不适用于普通聊天、纯本地文件操作或与 Tickly Todo 无关的 MCP。

## 核心约束

1. 先读取当前 Tickly MCP 的实时工具 schema；不要假定工具参数永远不变。
2. 用户可见的任务身份使用账号内 `serial`（例如 `#42`），不要把数据库 `id` 当作任务编号。
3. 除主题可按下一条规则取默认值外，信息不足时先追问。尤其不要擅自生成任务标题/描述，或选择不明确的父任务。
4. 主题候选按“用户明确提供的主题 > 当前项目名”的顺序确定。用户未明确提供主题时，使用当前 Git 仓库或工作区根目录名作为候选，不要使用当前应用子目录名；只有无法可靠识别项目根目录名时才询问用户。
5. 创建任务、更新 `topic` 或在项目内默认查询前调用 `list_topics`，由 AI 结合语义和项目命名习惯，判断候选与已有精确主题是否等价；不实现或假定字符串匹配算法。大小写、空格、连字符或下划线差异可支持高置信度等价判断，例如 `test-center`、`Test Center` 和 `test_center`。“相关”不等于“等价”；`test-center-api` 不得仅因名称包含 `test-center` 就自动合并。
6. 只有一个高置信度语义等价项时，直接复用 `list_topics` 返回的精确值；多个候选或信心不足时列出精确候选并请用户确认，确认前不写入；没有等价项时才使用原候选主题。
7. 在 Git 仓库或工作区内获取列表且用户未指定主题或“全部项目”时，按上述规则解析当前项目的精确主题，并把它作为 `list_tasks.topic`；用户明确指定的范围优先。
8. 用户未指定状态时使用后端 `active` 默认范围，只展示 `new` / `in_progress`；`completed` / `cancelled` 子任务不进入列表，已处理父任务仅可作为活动子任务的 `context_only` 结构上下文。用户明确要求全部或某个状态时按其要求传参。
9. 用户未指定排序时使用后端默认的 `priority desc`，同优先级按 `created_at desc`，无优先级放在最后。排序由后端 cursor 保证，不要逐页局部重排；用户明确指定排序时按实时 schema 传参。
10. 创建子任务使用 `create_task` 的 `parent_serial`，不要把父子关系写进描述文本。
11. 普通字段修改使用 `update_task`；状态修改只使用 `set_task_status`，状态值使用 schema 中的枚举。
12. `cancelled` 表示可恢复的“已废弃”状态，不是删除；进入该状态会清空 `completed_at`。任何由 AI 发起的废弃写入，操作前都必须明确告知用户这是状态变更而非删除。
13. 查询返回 `next_cursor` 时持续分页，直到满足用户范围；不能只处理第一页后声称“全部”。
14. 批量写入前先汇总目标数量和 serial，并在会产生写入时请求一次确认。逐项记录成功与失败；有失败时不得报告为全部成功。
15. Tickly MCP 没有删除工具。删除请求应明确说明无法执行，不得用清空内容、改状态或访问内部 API/数据库模拟删除；替代方案需用户明确同意。
16. 写操作完成后重新读取或使用工具返回值核对结果，并报告实际变更的 serial。

## 推荐流程

### 查询

选择最窄的只读工具：

| 目的 | 工具 |
| --- | --- |
| 列表、筛选、排序 | `list_tasks` |
| 单个任务及直接子任务 | `get_task` |
| 当前账号的精确主题值 | `list_topics` |
| 查找可作为父任务的根任务 | `find_parent_tasks` |

在项目内查询时，先调用 `list_topics` 解析当前项目的精确主题，再把它传给 `list_tasks`。用户没有指定状态或排序时保留后端的 `active`、`priority desc` 默认值；显式请求全部状态、其他状态、其他主题或其他排序时，以用户要求为准。保留并消费 `next_cursor`，后续页沿用完全相同的筛选与排序参数。如果用户使用模糊任务名称，返回候选并请求确认，不要默认选第一项。

### 创建或更新

1. 解析用户明确提供的标题、描述、主题、截止时间和父任务；未明确提供主题时，按核心约束使用当前项目根目录名作为候选。
2. 调用 `list_topics` 并由 AI 判断是否有唯一的高置信度语义等价项；有则复用返回的精确主题，无则使用原候选，歧义时先询问。
3. 缺少其他必需信息或无法可靠识别当前项目名时先询问；不要把可默认的主题视为缺失信息。
4. 写入前说明目标和范围；批量操作尤其要说明数量。
5. 创建用 `create_task`，普通字段用 `update_task`，状态用 `set_task_status`。
6. 记录每项结果；不要把工具错误包装成成功。

截止时间遵循实时 schema；当前 Tickly MCP 通常要求 RFC3339 date-time 字符串，不要自行传 Unix timestamp。

### 废弃或恢复任务

将任务设为 `cancelled` 前，明确说明这是可恢复的“已废弃”状态变更而非删除，且会清空该任务的 `completed_at`。

如果目标是父任务，必须按以下顺序操作：

1. 先调用 `get_task` 读取父任务和当前直接子任务。
2. 向用户列出父任务 serial、会随父任务一起废弃的 `new` / `in_progress` 直接子任务 serial，以及保持不变的 `completed` 直接子任务 serial。已有 `cancelled` 子任务也保持不变，不得声称它会被再次修改。
3. 明确提示：以后恢复父任务不会自动恢复这些子任务。
4. 等待用户明确确认；用户拒绝或取消时立即停止，不调用任何写工具。
5. 确认后才调用 `set_task_status`。级联由 API 在同一事务中完成，不要再逐个修改子任务。
6. 写入后再次调用 `get_task`，按实际返回报告父任务、实际级联废弃的子任务和保持完成的子任务；不得把操作前的预期当作成功结果。

将已废弃的父任务恢复为 `new`、`in_progress` 或 `completed` 前，也要先提示恢复父任务不会自动恢复子任务并等待明确确认。确认后只修改父任务，随后再次调用 `get_task` 核验并报告实际状态。

### 批量修改

先完整读取目标集合，再展开每个根任务组中的直接子任务，按 serial 去重后确定目标集合。跳过已经满足目标状态的任务；遇到单项失败继续处理其余项，但最终分别列出成功和失败。

“逾期”等条件必须依据返回的截止时间和账号时区判断；如果时区或边界不明确，先说明假设或询问用户。

### 删除或超出能力边界的请求

先确认当前工具列表没有相应能力，然后直接说明不能执行。不得调用不存在的工具、伪造删除结果，或建议绕过 MCP 的内部 API/SQLite。

## 输出要求

- 简短说明使用的 Tickly 工具和实际结果。
- 写操作至少报告 serial、成功/失败数量；批量操作给出失败项及原因。
- 无法执行时说明具体能力边界，并给出需要用户确认的安全替代方案。
